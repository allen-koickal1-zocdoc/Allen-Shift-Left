## Observations

- **The write path is never tested against real Dynamo.** `DynamoUserAccountDynamoPersistenceTests` covers reads only; every `PutAccount` assertion — including the conflict, replay, subset, and superset semantics that the API's 409 behaviour depends on — runs against `FakeUserAccountDynamoPersistence`. The fake's conditional-write semantics are asserted in detail (rows 65–75), but nothing proves real Dynamo behaves the same way.
- **14 of 23 API tests are `[Category("FakeOnly")]`.** Every functional API test — create, replay, reverse lookup, enum fidelity — is FakeOnly. The 9 tests that run against the real deployment are all authorization cases (rows 2–7, 20–22). Functionally, the deployed service is covered only by unit and fake-backed tests.
- **Authorization is covered symmetrically across all three endpoints.** Each of GET by id, PUT create, and POST reverse-lookup has the same trio: no token → 401, patient JWT → 403, and CSR JWT with the *opposite* scoped role → 403. That last case is the valuable one: it proves `UserAccountRead` and `UserAccountWrite` are enforced as distinct scopes rather than a single "is a service" check.
- **Error responses are deliberately non-revealing, and that is asserted.** Row 27 pins the generic `"Account not found."` on a reverse-lookup miss, and row 34 pins a 409 message that omits the conflicting account ids while verifying they are logged instead. These are the tests that would catch an identity-enumeration regression.
- **The `[Values]` enum tests are the highest-leverage rows here.** Rows 42–47, 55, and 56 expand over every enum member, so adding an issuer, identity type, or tenant with no matching switch case fails the build rather than silently mapping to a default. Row 23 is the API-level counterpart, pushing all 20 issuer × type × tenant combinations through serialization and storage.
- **2 of 85 tests are template scaffolding.** Both `ExampleTests.cs` files assert `1 + 1 == 2`; `UserAccounts.Web.IntegrationTests` contains nothing else.
