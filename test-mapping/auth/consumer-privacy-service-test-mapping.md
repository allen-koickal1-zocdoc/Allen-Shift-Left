## Observations

**The functional-test project is empty.** Row 308 is the only test in `tests/FunctionalTests/`, and it is scaffolding. There is no test that drives a CCPA request end to end — submit, verify by PIN, have each team upload, complete, download. Every stage is covered in isolation, and the seams between them are not.

**Rate limiting is the most heavily specified rule, and its correctness depends on a Dynamo query.** The 12-month limit is asserted at the unit level (rows 3–5, 11–12, 21, 25, 27, 29) and the query it rests on is asserted against real Dynamo (rows 279–281). Two carve-outs exist: requests dated before go-live do not count (rows 4, 11), and flagged test users are exempt (rows 20, 154, 265). The type filter in row 3 is subtle — a delete request does not consume the access allowance.

**Identity checks are applied asymmetrically between the access and delete paths, and the tests say so deliberately.** Row 108 asserts a delete task update *succeeds* with a non-matching NPI while row 115 asserts an access task update *fails* on the same. Both are named and both pass, so the difference is intended — but it means NPI is a weaker identifier on the deletion side. Anyone tightening one path should read both rows before assuming the looser one is a bug.

**Opt-out is fail-safe in every direction that matters.** A reconciliation write failure still returns opted out (rows 55, 63), the kill switches disable the *write* but never the *answer* (58, 59, 72), and the SPI and tracking axes are independent so one cannot silently override the other (row 50). Opt-out state is derived by recency from an append-only log (163, 166, 169, 170), which is why every one of those recency tests matters — a stable-sort regression flips someone's consent.

**The auditor is well-built instrumentation.** Rows 174–183 cover a shadow-read comparing the user-id-derived and patient-id-derived answers. It skips and tags rather than skipping silently (174, 175), reuses one read for two emissions (181), and swallows its own failures behind an error metric (183). It is a model for how to instrument a migration, and it should be deleted once the migration lands.

**Redelivery handling is inconsistent in one place worth flagging.** The stream processor short-circuits on already-submitted (224) and already-completed (230, 232) requests, but row 227 asserts an already-verified request is *reprocessed*. That may be intentional, but it is the one branch where a Dynamo stream redelivery does real work twice.

**Salesforce writes are upserts keyed on a deterministic external id** (row 255), which is what makes rows 243–246 safe under redelivery, and failures carry the task id and external id so they can be traced back (247). That is better failure hygiene than most integration code.

**Two matrices are the highest-leverage rows in the suite.** Rows 273 and 274 pin, across 30 cases, which teams are responsible for which request type and user type. A wrong entry means a team never receives a task and the request completes without their data — a compliance failure that would not surface as an error anywhere.

**Scaffolding and thin spots:** rows 202, 307, and 308 are template placeholders. `RecordProcessorTests` has a single test (256) for the Lambda's outermost handler, and `ClaimParserTests` has a single test (200) for the class that decides whether a caller is a patient or a practice user.
