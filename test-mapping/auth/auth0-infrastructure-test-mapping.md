Two independent suites live here:

- **C# (NUnit), 57 tests** under `tests/` — the Lambda that consumes Auth0 tenant log streams and turns them into Kafka events and Datadog metrics.
- **JavaScript (Jest), 142 tests** under `__tests__/unit/` — the Auth0 Actions themselves: the claim-enrichment, MFA-challenge, and custom-database scripts that run inside Auth0 on every login. Plus **1 Cypress smoke test**.

The JS half is the higher-stakes one: those scripts execute in Auth0's runtime on the live login path, and Jest is the only place they are exercised.

## Observations

**The Auth0 Actions are the highest-stakes code here, and Jest is their only net.** Everything under `actions/` executes inside Auth0's runtime on the live login path for every patient, provider, and internal-services user. There is no staging integration test that drives a real tenant through these scripts — the sole browser-level test in the repo is row 200, one authorization-code smoke test. If an Action regresses in a way Jest does not model, the first signal is a production login failure.

**Three Actions have no tests at all.** `actions/patient/add_patient_role.js`, `actions/patient/redirect.js`, and `actions/patient/require_zd_app_for_marketplace.js` ship with zero coverage. The last of those is an access gate — it decides whether a marketplace login is allowed to proceed — and it is untested.

**Practice scoping is the most carefully covered decision, and rightly so.** Rows 145–152 pin the full `practice_id` resolution precedence: user preference is honoured only when the practice is in the allowed list (147), an empty allowed *array* denies outright (151), but an empty allowed *string* falls through to connection metadata (152). Those last two differ, and the difference is load-bearing — the array case is a deny and the string case is a fallback. A refactor that normalised the two would silently change who can see which practice's data.

**MFA has three independent bypass paths, each pinned.** SSO connections bypass (rows 70, 71, 85, 86, 93, 94 — SSO beats even full SMS eligibility), `mfa_opt_out` bypasses (80–84, and only a real boolean `true` counts, so a stray truthy string cannot disable MFA), and the first login is exempt (60) — except when risk is elevated (63). Risk handling deliberately splits: a missing *confidence value* fails closed and challenges (65), but a missing *risk assessment object* does not (66). That asymmetry is intentional and would be easy to "fix" into a regression.

**The internal-services scope decision is a three-way intersection that cannot be widened from the outside.** Rows 96–98 each remove one leg: the request cannot ask for a scope the user lacks, the user cannot use a scope the app is not allowed, and permissions held on another resource server do not leak across. The empty-request default fails closed to baseline `CsrUser` unless the client explicitly opts in (103–105). Four separate fail-open tests (110–112) confirm a Management API outage degrades to *no role claim* rather than a broken login — the right trade, but it means a Management API incident silently downgrades authorization rather than alerting.

**The monolith is still the source of truth for email verification, and the tests say so.** Rows 160 and 172 both assert that Auth0 is told the email is verified regardless of what the monolith reports. That is a deliberate migration decision, not an oversight, and it is worth knowing it is asserted in two places: if the monolith ever stops verifying emails, Auth0 will not catch it.

**The log-stream Lambda distinguishes four outcomes and never conflates them.** Matched, processed, ignored, and dropped are mutually exclusive (row 16), dropped always carries a reason tag (13–15, 21), and ignored is tagged by tenant and event type (17). Producer failures rethrow deliberately so EventBridge retries (8, 9) and malformed SQS bodies rethrow so SQS redrives (30, 31) — losing an auth event silently is treated as worse than a retry storm.

**Correlation-id parsing is defensive in every direction** (rows 22–27): a bare GUID, a wrong prefix, an illegal base64url character, and an absent value all resolve to nulls with the raw value passed through, never an exception on the log path.

**Two exhaustiveness guards are the highest-leverage rows in the C# suite.** Row 52 asserts every known tenant has an explicit type mapping and row 53 asserts an unmapped tenant throws — together they make adding a tenant without a type a test failure rather than a runtime surprise. Row 33's 48-case table does the same for the Auth0 log-code → Datadog metric mapping.

**Scaffolding:** row 57 (`FakeTests`) is template boilerplate with no product coverage. `cdk/jest.config.js` points at `<rootDir>/test` for `**/*.test.ts`, but `cdk/test/` does not exist — the CDK infrastructure code in this repo has no tests.
