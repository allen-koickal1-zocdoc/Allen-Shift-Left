This repo is the **fake auth server** (`authentication-mock-apis`, per `plinth.yaml`) that every other Zocdoc service points at in its own integration tests: it mints JWTs, serves JWKS and OIDC discovery documents, and stands in for OpenFGA. All 99 tests live in the single `Zocdoc.Auth.Mock.Tests` project and drive the mock over HTTP through a test client. A regression here silently changes the auth behaviour that dozens of downstream test suites assume.

## Observations

- **This repo is a test dependency for the whole org, and it has no consumer-parity coverage.** The only file that would check the mock against the real auth service — `ApiParityTests.cs` — contains a single `[Ignore]`d test (row 99). Everything else asserts that the mock behaves the way the mock is written to behave. If the real Auth0 or FGA contract drifts, nothing here fails; the downstream suites keep passing against a stale fake.
- **Token shape is pinned hard, which is the right call.** Rows 35–55 and 56–65 assert issuer, audience, kid, algorithm, subject, and lifetime on every token flavour (Zocdoc, Cognito, Auth0 patient tenant, Auth0 practice tenant, Auth0 Action). Combined with the JWKS test (row 85, which pins exactly 4 keys and the first two kids), a change to the signing keys or issuer URLs breaks loudly here rather than mysteriously in a downstream repo.
- **The practice-claim suppression migration is the most heavily covered behaviour.** Six tests across two files (rows 38–40, 58–61) cover suppression on and off, per legacy claim type, with and without a practice identity, and supplied via both headers and JWT params. That density suggests an in-flight migration off the legacy `practice`/`practice.rbac_*` claims onto `practice.is_practice_user`.
- **The FGA mock has two independent stores and both are covered, including their union.** `/write` feeds a real tuple store, `/setup` feeds a simpler allow/deny/error override store, and row 26 pins that `list-objects` unions and dedupes across both. Rows 30–34 cover injectable 429/500 failures with reset semantics — this is how downstream services exercise FGA-outage handling, so it is worth more than it looks.
- **Four legacy deny sentinels are load-bearing.** Row 7 pins `user:unauthorized`, `organization:notfound`, `practice:notfound`, and relation `ua_unapproved` as always-deny. Downstream tests use these magic strings to force a deny without writing tuples; renaming any of them would silently turn other repos' negative tests into positives.
- **A deliberate quirk worth knowing: the mock does not verify assertion signatures.** Row 67 asserts a 200 for an unverifiable JWT assertion. That is intentional for a fake, but it means no downstream test can exercise signature-rejection through this mock.
- **One naming inconsistency.** Row 71 is named `..._Unauthorized` but asserts 403 Forbidden, while its two neighbours with the same suffix assert 401. The assertion matches the FGA controller's equivalent test (row 2), so the status is likely correct and the name is wrong.
